# PWA 离线化方案（离线可玩 + 后台同步）

> 状态：**方案稿，未实现**
> 目标：断网时不是"看离线提示页"，而是**游戏能继续玩**，联网后自动同步。

---

## 一、现状（已确认）

`static/sw.js` 缓存名 `mono-pwa-v4`，当前策略：
- 导航请求：**网络优先**，失败回退「带版本戳的壳」；版本对不上就返回自带的离线提示页 ✓
- 排除项：`/api/`、`/uploads/`、`socket.io`、`/music/stream/`、带 `range` 的请求 ✓
- ⚠️ **一次事故教训**：把 `/` 缓存后不管 → 断网端出几个月前的旧首页 ✗
  → 所以现在是**带版本戳**的壳 ✓ 这个机制要保留 ✓

**结论**：现在的离线是"**优雅降级**"（告诉你没网），不是"**离线可用**" ✗

---

## 二、目标分级

| 级别 | 内容 | 价值 |
|---|---|---|
| **L1** | 静态资源离线（CSS/JS/图标/棋子图） | 弱网下打开快，几乎无成本 |
| **L2** | **单人游戏离线可玩**（24点/数独/扫雷/华容道/汉诺塔/跳一跳） | 地铁、电梯里能玩 ✓ |
| **L3** | **成绩后台同步**（联网后自动上传，不丢分） | 离线玩也有意义 ✓ |
| **L4** | 象棋残局/人机离线可玩 | 依赖 AI，工作量大 ✗ |

**建议先做 L1 + L2 + L3** ✓（L4 等 AI 对手做完再说）

---

## 三、L2 实现要点（单人游戏离线）

### 关键前提：这些游戏**本来就是纯前端**的 ✓
24点/数独/扫雷/华容道/汉诺塔/跳一跳 —— 逻辑全在浏览器 ✓
**唯一的联网点是"提交成绩"** ✗ → 把它变成"可失败、可重试"就行 ✓

### 做法
1. `sw.js` 的 `CACHE` 里加：这些游戏的模板 + 依赖的 JS/CSS ✓
   （它们不是导航请求 ✗ 要单独加进 precache 列表 ✓）
2. 页面本身已被壳缓存 ✓ 断网能打开 ✓（现在就能 ✓ 只是资源没缓存）
3. **游戏逻辑不用改** ✓

---

## 四、L3 实现要点（成绩后台同步）

### 核心：把"提交成绩"从"必须成功"改成"先存本地、联网再传"

```
玩游戏 → 成绩写入 IndexedDB（pending 队列）
         ↓
    尝试 fetch 提交
         ↓ 成功 → 出队
         ↓ 失败 → 留在队列
         ↓
联网时（online 事件 / 页面加载 / SW 的 sync 事件）→ 逐条重放
```

### 具体改动
1. **新增 `static/js/offline-queue.js`**：
   - `queueScore(field, value)`：写 IndexedDB
   - `flushQueue()`：逐条 POST，成功出队
   - 监听 `window.addEventListener('online', flushQueue)` + 页面加载时也跑一次
2. **`_submit_score_common` 的前端调用点**改成走 `queueScore` ✓
   （**服务端不用改** ✗ —— 幂等性由"同分不重复写"保证 ✓ 见下）
3. **服务端幂等**：成绩提交用「更大才更新」✓ **天然幂等** ✓
   重复提交同一个成绩不会出错 ✓（时间类游戏同理 ✓）
4. **UI 反馈**：离线提交时 toast「已离线记录，联网后自动上传」✓
   页头显示一个「N 条待上传」小角标 ✓

### 为什么不用 Background Sync API
`sw.js` 里可以用 `SyncManager` ✗ 但 **iOS Safari 不支持** ✗
→ **用 `online` 事件 + 页面加载兜底** ✓ 兼容性最好 ✓

## 五、L1 实现要点（静态资源）

1. `sw.js` 的 `CACHE` 版本号 **`mono-pwa-v4` → `v5`** ✓（改策略必须升 ✓ 否则旧缓存不清 ✗）
2. precache 列表加：`static/css/base.css`、`static/js/*.js`（marked/purify/highlight）、
   图标、`static/xqm/*.ogg`（BGM 离线也有 ✓ —— hmm，2.4MB ✗ 可选 ✗）
3. **排除项别动** ✓（`/api/`、`socket.io`、`/music/stream/`、`range` 请求 ✗ 动了会出大问题 ✗）

## 六、风险与注意事项

| 风险 | 应对 |
|---|---|
| **缓存炸存储** | precache 只放必需资源；BGM 这种大文件**不缓存** ✗ |
| **旧壳问题**（历史事故） | 保留「带版本戳的壳」机制 ✗ 别退化成"缓存 `/` 不管" ✗ |
| **重复提交成绩** | 服务端「更大才更新」已幂等 ✓ 但**时间类**要确认 ✓ |
| **队列无限增长** | 队列上限 200 条，超了丢最旧的 ✓ |
| **多标签页并发 flush** | 用 `localStorage` 加个简单锁 ✗ 避免重复上传 ✓ |
